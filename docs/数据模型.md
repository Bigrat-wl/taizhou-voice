# 泰州方言通 数据模型设计（v2）

> 日期：2026-08-19 · 状态：已定稿（v2），与 `backend/app/models.py` 对齐，后续字段变更同步此处
> 定位：表结构的字段级说明，为接口与建表提供唯一权威来源。

---

## 1. 设计原则

1. **先定实体，再写接口**：字段和关系先想清楚，接口只是数据的出入口。
2. **主键 vs 业务标识**：数据库主键（自增 `id`）只给系统内部用；用户唯一登录标识是 `email`，展示名用 `nickname`（允许重名）。
3. **时间统一中国时区**：存 `datetime`（`Asia/Shanghai`，UTC+8），接口返回带 `+08:00` 的 ISO 8601；相对时间由前端格式化。
4. **密码不落明文**：`password_hash` 用 bcrypt，任何接口不返回该字段。
5. **演示期不做软删除**：删除即真删；`deletedAt` 等字段等到真需要再加。
6. **音频只存路径不存 blob**：音频落 `backend/data/audio/`，库里存相对路径，后期迁 COS 只改读写层。
7. **计数现算不冗余**：正确数、点赞数、总分都用 `COUNT`/`SUM` 实时算，量级小，不维护计数器字段。

---

## 2. 实体总览

```
Sentence ──< Recording >── User
                 │
                 └──< Like >── User
```

- 一句子：可被多次挑战（1-N 录音）。
- 一用户：多条录音（1-N）、多条转写历史（1-N）、点多个赞（1-N）。
- 录音：属于一个句子 + 一个用户；可被多个用户点赞（1-N）。
- **正确数** = 某用户 `score >= 60` 的录音数量（实时 `COUNT`）。
- **点赞数** = 某录音被 `like` 的数量（实时 `COUNT`）。

## 3. 实体定义（对齐 `models.py`）

### 3.1 Sentence 句子

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | Integer | PK 自增 | |
| text | Text | 必填 | 普通话参考文本（评分基准） |
| dialect_text | Text | 必填 | 方言文本（展示用） |
| category | String(64) | 默认 "" | 分类（日常/问候/饮食…） |
| difficulty | Integer | 默认 1 | 难度等级 |
| created_at | DateTime | 默认 now(Asia/Shanghai) | |

> 单词（word）题库**后置**：演示期只做句子。届时扩展 `Recording` 加 `word_id` 或引入 `item_type` 多态，本次不预留，避免过度设计。

### 3.2 User 用户

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | Integer | PK 自增 | |
| email | String(255) | unique, 必填 | 登录邮箱（唯一标识） |
| password_hash | String(255) | 必填 | bcrypt，**永不返回** |
| nickname | String(64) | 必填 | 显示昵称（允许重名） |
| total_score | Integer | 默认 0 | 累计总分（整数分，每次评分累加） |
| created_at | DateTime | 默认 now(Asia/Shanghai) | |

> 演示期最简用户系统：邮箱 + 密码。`openid`（微信登录）等到真接微信时再加（可空字段）。

### 3.3 Recording 录音 + 评分

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | Integer | PK 自增 | |
| sentence_id | Integer | FK → sentences.id, 必填 | 关联句子 |
| user_id | Integer | FK → users.id, 必填 | 关联用户 |
| audio_path | String(512) | 必填 | 音频相对路径，见 §4 |
| score | Integer | 默认 0 | 评分（0~100 整数） |
| created_at | DateTime | 默认 now(Asia/Shanghai) | |

> **无 `level` 字段**：等级由前端按分数映射颜色（≥90 绿「优秀」/ 60–89 黄「中等」/ <60 红「不及格」），后端只给分数。**及格线 = 60**，`score >= 60` 计入正确数。

### 3.4 Like 点赞关系

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | Integer | PK 自增 | |
| recording_id | Integer | FK → recordings.id, 必填 | 被点赞的录音 |
| user_id | Integer | FK → users.id, 必填 | 点赞人 |
| created_at | DateTime | 默认 now(Asia/Shanghai) | |

> `(recording_id, user_id)` **联合唯一**，防止重复点赞；取消点赞即删行。点赞数 = `COUNT(Like WHERE recording_id=?)` 现算。

### 3.5 Translation 转写/互转历史

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | Integer | PK 自增 | |
| user_id | Integer | FK → users.id, 必填 | 关联用户 |
| source_text | Text | 默认 "" | 源文本 |
| result_text | Text | 默认 "" | 结果文本 |
| direction | String(32) | 默认 "" | 方向（`asr` / `tts` / `dialect2mandarin` / `mandarin2dialect`） |
| created_at | DateTime | 默认 now(Asia/Shanghai) | |

> TTS/互转结果是音频，`result_text` 存文本侧内容；音频落盘路径如需留存可复用 `audio_path` 思路（当前未加，用到再补）。

## 4. 音频文件存储约定

- 目录：`backend/data/audio/`（不进 git）。
- 命名：`{sentence_id}_{user_id}_{ts}.wav`（挑战赛）；TTS/互转用 `tts_{ts}.wav`、`conv_{ts}.wav`。
- 格式：统一 16kHz 单声道 WAV，上传后后端用 librosa/ffmpeg 转码。
- 库里只存相对路径（`audio/xxx.wav`），不存绝对路径，方便换机器/迁 COS。

## 7. 管理平台与训练平台（预留 · 后置）

> 状态：需求已定，**代码暂不实现**。演示期只做用户平台，本节为后续管理/训练平台预留字段与架构决策，避免到时改表。

### 7.1 三端架构

```
用户平台（采集 + 消费）────┐
管理平台（数据管理 + 标注）──┼──▶ 共享数据池（同一 DB + 同一存储）
独立训练机（GPU 训练）──────┘
```

- 用户平台、管理平台、训练机三端**共享同一数据池**，靠 `status`/`source` 字段筛选，不做物理隔离。
- 训练机物理独立跑（GPU 微调），从数据池拉 `approved` 数据，产出模型回灌 `models/`。
- 管理平台负责基本功能操作（句子/语料/录音的增删改、审核、上下线），后续加**数据标注**。

### 7.2 数据池筛选机制（双向流动）

- 管理平台录入句子 `draft` → 审核 → `published` → 用户平台可见。
- 用户录音进数据池 → 管理平台审核 → `approved` → 训练可用。
- 「用户看到的数据」和「训练用的数据」是**同一张表的两个视图**，靠 `status` 区分，不是两份数据。

### 7.3 预留字段清单（代码暂未实现）

| 表 | 字段 | 取值 | 用途 |
|----|------|------|------|
| `sentences` | `status` | `draft` / `published` / `archived` | 用户平台只查 `published`；管理端看全部 |
| `sentences` | `source` | `manual` / `collected` | 语料来源（管理录入 / 用户收集） |
| `recordings` | `status` | `pending` / `approved` / `rejected` | 训练只拉 `approved` |
| `annotations`（新表） | `recording_id` + `annotator` + `content` + `created_at` | — | 数据标注（后续），独立建表不污染 `recordings` |

### 7.4 存储迁移（训练机独立的触发条件）

- 训练机物理隔离后，本地 `backend/data/audio/` 与 `models/` 无法三端共享，需迁对象存储（腾讯云 COS）。
- 数据库 SQLite 不支持多机，届时换 PostgreSQL 或让训练机远程拉数据。
- 设计已预留：音频只存相对路径，迁 COS 只改读写层，数据模型不动。

### 7.5 两步走策略

1. **现在（演示期）**：只把 `sentences.status/source`、`recordings.status` 记入本文档，**代码不动**（标注表也不建）。
2. **管理平台启动时**：走诸葛定任务书，一并规划「管理接口 + 标注表 + COS 迁移」。
