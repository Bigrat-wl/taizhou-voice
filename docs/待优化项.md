# 待优化项

> 记录当前实现的临时方案和后续优化方向。

---

## 1. 转写翻译方案（规则映射 → 大模型翻译）

**当前实现**：基于平行句对的规则映射（`translate_service.py` + `make_translate_map.py`）

**问题**：
- 覆盖范围有限，只能翻译已入库的句对和自动提取的词级规则
- 无法处理未见过的方言表达
- 规则质量依赖平行语料的质量和数量
- 维护成本高：每新增方言表达需手动更新语料并重新生成规则

**关键问题**：目前大模型（Qwen3-ASR）只能输出谐音文本，其转译是由映射来完成的。这涉及到模型是如何训练的问题，因此需要对模型训练的模式进行探讨。

**优化方向**：
- 替换为大模型翻译（如 Qwen3、GPT-4 等），输入谐音字输出普通话
- 或训练专门的方言→普通话翻译模型
- 保留规则映射作为 fallback（大模型未命中时回退）

**优先级**：中（演示期规则映射够用，长期必须替换）

**触发条件**：
- 用户反馈翻译不准确
- 需要支持更多方言表达
- 语料库扩充到 100+ 句对后仍覆盖不足

## 2. 评分方案（文本相似度 → 三维评分）

**当前实现**：编辑距离计算识别文本与参考文本的相似度（0-100 整数）

**问题**：
- 只衡量文本相似度，不考虑发音、声调、口音
- 方言发音准确但用词不同时可能被误判

**优化方向**：
- 三维评分：发音准确度、声调相似度、口音特征
- 可结合音频特征（MFCC、pitch 等）进行综合评估

**优先级**：低（演示期文本相似度够用）

---

## 3. 用户系统（邮箱密码 → 微信登录）

**当前实现**：邮箱 + 密码注册/登录（JWT 鉴权）

**问题**：
- 演示期最简方案，不适合真实用户
- 无密码找回、邮箱验证等功能

**优化方向**：
- 微信小程序登录（openid）
- 手机号 + 验证码
- 第三方 OAuth（微信、QQ）

**优先级**：低（演示期邮箱密码够用）

---

## 4. 存储方案（本地 → 对象存储）

**当前实现**：音频文件存本地 `backend/data/audio/`，路径存 SQLite

**问题**：
- 单机存储，无法扩展
- 无法多机共享（训练机、管理平台）

**优化方向**：
- 迁移至腾讯云 COS（对象存储）
- 数据库换 PostgreSQL（多机共享）

**优先级**：低（演示期本地存储够用）

---

## 5. TTS 语音合成（pyttsx3 CPU 回退 → CosyVoice2 GPU）

**当前实现**：CosyVoice2（GPU）+ pyttsx3（CPU 回退）

**问题**：
- pyttsx3 是系统 TTS，无方言效果
- CosyVoice2 实际推理需在 GPU 环境验证

**优化方向**：
- 确保 GPU 环境稳定可用
- 微调 CosyVoice2 以支持泰州方言音色

**优先级**：中（演示期 pyttsx3 够用，长期需 GPU）
